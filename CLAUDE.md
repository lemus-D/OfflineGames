# Project Context

Prioritize readability over cleverness. Ask clarifying questions before making
architectural changes.

This file is short on purpose. The long versions are in `docs/`.

## About This Project

We are making small games that are played offline, sold from a website. Each
game is an **installable PWA**: the customer buys it, opens it, installs it, and
a service worker precaches everything so it runs with no network.

`moon-rover` is a git submodule pointing at a finished reference game (REGOLITH).
It is the quality bar — "fun to play, good graphics". Fetch it with:

```bash
git submodule update --init --depth 1
```

Read `moon-rover/README.md` and `moon-rover/docs/ARCHITECTURE.md`. It is a
complete 3D game in
379 KB gzipped with zero asset files, and it is the proof that the approach here
works. Copy its doctrine, not necessarily its structure.

Right now the two games in this repo (`Sharky/`, `Yes-General/`) are **planning
only**. Nothing is built. Sharky's design is settled and specified; Yes-General
still needs a design conversation.

## Standards

Non-negotiables. Each one is explained in `docs/TECHNICAL-DECISIONS.md`.

1. **No build step, no runtime dependencies.** Plain ES modules across real
   files, served by a zero-dependency static dev server. The source in the repo
   is the thing that runs.

2. **All art and audio are generated by code. Zero asset files.** No images, no
   sound files, nothing to license. This is the doctrine that makes the project
   viable.

3. **Never use `Math.random()` in game logic.** Seed everything, and keep
   simulation on a fixed timestep separate from rendering. This is what keeps a
   verifiable leaderboard possible later; retrofitting it is a rewrite.

4. **Namespace and version every storage key** — `sharky.v1.profile`.
   `localStorage` is scoped to an origin, not a path, so games on the same domain
   share one store. Never key saved state by array index.

5. **Keep content in data, not in logic.** Upgrades, animals, techs and missions
   are rows in a table applied by one generic function. The reference project
   documents what the alternative costs: *"Fix this before writing story content,
   not after."*

6. **Verify in the running game, not by reasoning.** Claims about behaviour that
   were not observed are not findings. Run it, then say it works.

7. **Don't trade fun, feel or clarity for bytes.** Download size is not a
   constraint here — a complete 3D game is 379 KB and even 5 MB downloads in
   under two seconds. Keep games small as a consequence of rule 2, not as a goal.

## Common Commands

```bash
git submodule update --init --depth 1   # fetch the moon-rover reference
cd moon-rover && npm start              # run it at http://localhost:5173
```

The single-file spike needs no server — open `spikes/single-file-canvas-probe.html`
directly in a browser to see the procedural drawing technique.

Each game will carry its own zero-dependency `server.js` for development.
Service workers require a secure context, so a PWA cannot be tested from
`file://` — always use the dev server.
