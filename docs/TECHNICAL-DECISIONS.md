# Technical decisions

Settled questions, so nobody re-opens one by accident. Each entry says what was
decided, why, and what would have to change for it to be worth revisiting.

If you disagree with something here, say so before building against the
opposite assumption. Do not quietly diverge.

Evidence for the platform claims is in
[PLATFORM-CONSTRAINTS.md](PLATFORM-CONSTRAINTS.md).

---

## D1 — Each game ships as an installable PWA

**Decided.** Not a file download, not a native app, not a plain web page.

The customer buys on the website, opens the game, and installs it. A service
worker precaches everything so it runs with no network.

Verified working with the server killed, including external ES module imports
served from cache.

*Why not a file download:* a downloaded `.html` runs on `file:`, which blocks
external ES modules, import maps, `fetch()`, IndexedDB and service workers, and
is painful to open on a phone. These games are mobile-shaped.

*Reopen if:* the target becomes desktop-only, or a storefront requires a real
installable binary.

---

## D2 — No build step. Plain ES modules. No runtime dependencies

**Decided.** Copied from `moon-rover`, which proves it works at 7,300 lines.

Author in `src/` as real modules across real files. Serve with a zero-dependency
static server for development. There is nothing to install and nothing to
compile, so the source in the repo is the thing that runs.

Consequences to accept: no TypeScript, no minification, no tree-shaking. We ship
readable source and let gzip do the work — `moon-rover` is 1.61 MB raw and 379 KB
over the wire.

*Reopen if:* a game genuinely needs a library that is only distributed as a
bundle, or release packaging (not development) needs a minify pass.

---

## D3 — All art and audio are generated by code. Zero asset files

**Decided.** This is the doctrine that makes the whole project viable.

`moon-rover` is a complete 3D game in 379 KB gzipped, of which 266 KB is the
vendored three.js and only **113 KB is the game itself** — every texture, sound,
rock and star included, because they are all arithmetic.

Justify this by the reasons that hold: no asset pipeline, nothing to license,
unlimited variety from one code path, and art that is correct at every size.
**Do not justify it by download size** — see D4.

*Reopen if:* a specific game needs a look that procedural generation genuinely
cannot reach. Argue it per-game, not globally.

---

## D4 — Download size is not a design constraint

**Decided**, and this one corrects an earlier assumption worth stating plainly.

At 25 Mbps: the canvas spike is 6.7 KB and downloads in 0.002 s; `moon-rover` is
379 KB and downloads in 0.12 s; even a hypothetical 5 MB asset-heavy game takes
1.6 s. A paying customer tolerates far more than a casual visitor.

So keep games small as a natural consequence of D3, but never trade fun, feel or
clarity for bytes. If spending 300 KB makes a game better, spend it.

---

## D5 — Sharky renders with Canvas 2D and no library

**Decided.** No three.js, no Phaser, no Pixi.

Measured library cost, minified and gzipped: `kontra` 11 KB, `kaplay` 67 KB,
`excalibur` 143 KB, `pixi.js` 225 KB, `phaser` 343 KB, `three.js` 250 KB. None of
them is expensive by D4, so this is not a size decision — it is a simplicity
decision, consistent with "readability over cleverness".

WebGL2 does work in this context if a later game wants 3D. `moon-rover` remains
the reference for how to do that.

*Reopen if:* a 2D scene needs thousands of independently transformed sprites,
which is where Canvas 2D actually falls down.

---

## D6 — Creatures come from one parametric body plan, not sprites

**Decided.** A species is roughly a dozen numbers — body depth, snout sharpness,
tail kind and span, dorsal and pectoral size, eye size, jaw, pattern, spine
flexibility, and a small palette. One drawing function reads those numbers.

This matters specifically because the game is about growing: the same animal is
drawn at 14 px as prey and at 400 px as a player. A sprite sheet cannot do that
without shipping several resolutions, and a new species costs a line of data
rather than an art commission.

Animation is procedural too: a travelling sine wave down the spine is what makes
a fish read as swimming.

**Where the `moon-rover` approach does NOT transfer:** the Moon is noise, so
fractal noise genuinely produces a lunar surface. Nothing about noise produces a
charismatic animal. Creatures need parametric *shape construction*; only the
environment (caustics, light shafts, murk, particulate, kelp) is a noise problem.
Do not try to solve creature art with `fbm()`.

Working reference: `spikes/single-file-canvas-probe.html` draws sixteen distinct
species from one body plan at sizes from 18 to 150 px.

## D7 — Shared code is copied, not shared

**Decided.** No shared engine package, no common `core/` imported by every game.

When a game needs seeded noise, input handling or save logic, copy the file in
and let it diverge. Extract a shared module only once two games have
independently converged on the same interface.

*Why:* a premature shared engine is the classic trap, and it fights the no-build,
no-dependency rule. The cost of copying 80 lines of noise functions is far lower
than the cost of a layer that has to serve an arcade game and a turn-based
strategy game at the same time.

*Reopen if:* three games are maintaining the same file and the drift is causing
real bugs.

---

## D8 — Saves are namespaced, versioned, and keyed by name

**Decided.** Three separate rules, all mandatory.

**Namespace every key.** `localStorage` is scoped to an origin, not a path, so
`example.com/sharky/` and `example.com/yes-general/` share one store. Prefix
everything: `sharky.v1.profile`.

**Version the schema.** Store `{ schema: 1, ... }` and migrate explicitly on
bump. A save that cannot be read should fall back to a fresh profile, never to a
mangled one.

**Never key state by array index.** `moon-rover`'s `ARCHITECTURE.md` documents
exactly what that costs: its anomaly state is a bare array of codes re-keyed by
position, so any change to world generation silently moves flags onto the wrong
objects, and the only reset lever is bumping a magic string. Use named keys.

Also ship an export/import save code. Storage can be evicted, and a lost
progression profile in a paid game is a refund request.

---

## D9 — The simulation is deterministic, and separate from rendering

**Decided.** No `Math.random()` anywhere in game logic. Seed every generator, and
run simulation on a fixed timestep independent of the render loop.

This costs almost nothing now and is the only thing that keeps a *verifiable*
leaderboard possible later. If the simulation is deterministic, a run is a seed
plus an input list — a few kilobytes — which a server can re-simulate to check a
submitted score. Retrofitting determinism into a finished game is close to a
rewrite.

`moon-rover` demonstrates the pattern: one seeded `core/rng.js` shared by the CPU
and the GPU so the two can never drift.

---

## D10 — Offline local scores now, leaderboards later

**Decided.** Track a local best. No backend, no accounts, no network calls.

Be clear-eyed about what a future leaderboard can be: `localStorage` is
player-editable, so anything an offline client submits is a claim, not a fact. A
later leaderboard either accepts that and is a fun list rather than a ranking, or
validates server-side by replaying inputs — which is only available because of
D9.

---

## D11 — No DRM

**Decided.** The game ships as readable HTML and JavaScript, so it can be opened,
copied and reshared, and an offline licence check runs on the customer's machine
with no server to appeal to. There is no technical fix within D1.

Do not spend effort here. Price and position as indie storefronts already do.

---

## D12 — Sharky's core design

**Decided** in conversation, recorded here so it is not re-litigated. The full
spec is in [../Sharky/SHARKYPLAN.md](../Sharky/SHARKYPLAN.md).

- **Free swim** in a 2D plane with the camera following. Not forced auto-scroll.
- **Hunger and predators together.** A draining meter forces you to keep eating;
  bigger creatures eat you.
- **Two progression layers.** Persistent: unlock new animals at milestones, each
  with its own upgrade pool. Per-run: randomised roguelite upgrade picks, so no
  two runs are the same.
- **Multiple animals with genuinely different eating rules**, not reskins. The
  rule differences are the reason to play a different animal.
